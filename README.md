# 2D SLAM Simulation in MATLAB

A modular 2D Simultaneous Localization and Mapping (SLAM) simulation implemented in MATLAB. The project combines a known ground-truth indoor environment, autonomous waypoint-based exploration, a virtual 360° LiDAR, MATLAB `lidarSLAM`, pose-graph loop closure, occupancy-map reconstruction, LiDAR/RANSAC perception, local planning, recovery behavior, logging, live visualization, and final performance analysis.

> **Important:** This is a software simulation. It does not require a physical robot, physical LiDAR, ROS, Gazebo, Simulink, or an external dataset. The LiDAR is generated by ray-casting against the simulated ground-truth occupancy grid.

---

## 1. Project Objective

The goal of this project is to demonstrate an end-to-end 2D SLAM pipeline rather than only using a SLAM function in isolation.

The complete flow is:

```text
Ground-Truth Environment
        ↓
Robot Initialization
        ↓
Exploration Waypoint Generation
        ↓
Robot Navigation
        ↓
Collision Detection / Recovery
        ↓
Virtual 360° LiDAR
        ↓
Scan Movement Gate
        ↓
MATLAB lidarSLAM
        ↓
Scan Matching + Pose Estimation
        ↓
Loop Closure Detection
        ↓
Pose-Graph Optimization
        ↓
Occupancy Map Reconstruction
        ↓
RANSAC Wall Extraction
        ↓
Map Filtering + Opening Detection
        ↓
Trajectory / Error / Velocity Analysis
```

The project keeps the ground-truth map separate from the reconstructed SLAM map so that the estimated trajectory and map can be evaluated against a known reference.

# 7. Complete Pipeline

## Step 1 — Ground-Truth Environment

`createEnvironment.m` generates the known simulated environment.

This map is used by the simulator for:

- collision checking
- LiDAR ray casting
- environment generation
- reference trajectory evaluation

The ground-truth map is **not** the SLAM result.

The SLAM map is reconstructed later from the simulated sensor scans.

## Step 2 — Robot Initialization

`createRobot.m` creates the simulated robot.

The robot state contains its pose and motion-related information.

The pose is represented as:

```text
[x, y, theta]
```

where:

- `x` = position along X
- `y` = position along Y
- `theta` = heading angle

The starting pose is:

```text
[1.2, 1.2, 0]
```

---

## Step 3 — Exploration Waypoints

`generateWaypoints.m` creates exploration points over reachable free space.

The waypoint system uses:

- waypoint spacing
- obstacle clearance
- reachable-space information
- wavefront-style ordering

The purpose is to make the robot explore the environment rather than simply travel from one fixed start point to one fixed goal.

# 9. Virtual LiDAR

`simulateLiDAR.m` implements the virtual 2D LiDAR.

It is intentionally independent of the SLAM system.

Its pipeline is:

```text
Ground-Truth Map
      ↓
Ray Casting
      ↓
Range Measurements
      ↓
Gaussian Noise
      ↓
lidarScan
```

## Ray-Casting Algorithm

For every LiDAR ray:

1. Calculate the ray angle in the robot frame.
2. Convert the ray direction into the world frame using robot heading.
3. Move along the ray in small increments.
4. Check the occupancy grid.
5. Stop at the first occupied cell.
6. Record the hit distance.
7. If no obstacle is detected, use the maximum range.
8. Add Gaussian measurement noise.
9. Clamp the range to the valid sensor limits.
10. Return a MATLAB `lidarScan`.

The current sensor configuration produces 360° scans with 1° angular resolution.

---

# 10. Scan Movement Gating

The simulation runs at a 0.05-second time step, but the robot does not need to send a new LiDAR scan to SLAM at every single simulation step.

A movement threshold is used:

```text
Translation threshold = 0.20 m
Rotation threshold    = 8°
```

This reduces redundant scan processing.

It also keeps the scan spacing consistent with the movement threshold used by `lidarSLAM`.

# 13. Coordinate-Frame Alignment

MATLAB's SLAM system starts in its own coordinate frame.

The simulated robot, however, starts at:

```text
[1.2, 1.2, 0]
```

Therefore, the first accepted scan establishes the transformation between the SLAM frame and world frame.

For a 2D pose:

```text
[x_slam, y_slam, theta_slam]
```

the aligned pose is approximately:

```text
x_world = cos(theta0)x_slam - sin(theta0)y_slam + x0

y_world = sin(theta0)x_slam + cos(theta0)y_slam + y0

theta_world = wrap(theta_slam + theta0)
```

This makes trajectory comparison with ground truth meaningful.

---

# 14. Loop Closure

Loop closure is one of the most important parts of the system.

When the robot returns to an area it has previously observed, the SLAM system can create a constraint between the current pose and an earlier pose.

These constraints allow the pose graph to correct accumulated drift.

Configured values:

```text
Loop closure threshold = 200
Search radius          = 3.0 m
Optimization interval  = 5 loop closures
```

The project counts actual newly reported loop-closure edges.

---

# 15. Occupancy Map Reconstruction

`buildOccupancyMap.m` reconstructs the map using:

```text
Accepted scans
     +
Optimized poses
     ↓
Transform to world frame
     ↓
Occupancy map
     ↓
insertRay()
```

For each accepted scan, its LiDAR rays are inserted into the occupancy map at the corresponding estimated pose.

Therefore:

```text
SLAM Map ≠ Ground Truth Map
```

The SLAM map is reconstructed from sensor information.

---

# 16. Occupancy Map Performance Optimization

Rebuilding the entire map after every accepted scan would repeatedly process the full scan history.

The project therefore caches the last reconstructed map.

The current implementation rebuilds after:

```text
10 newly accepted scans
```

Between rebuilds, the cached map is reused.

This significantly reduces unnecessary repeated map construction.

---

# 17. Map Boundary Handling

The reconstructed SLAM trajectory may potentially extend outside the original:

```text
X = [0, 20]
Y = [0, 15]
```

map limits.

`buildOccupancyMap.m` checks the transformed pose bounding box.

If poses are outside the nominal limits, the map is padded before inserting the scans.

This prevents the reconstructed map from being silently clipped.

# 19. RANSAC Wall Extraction

`extractWallSegments.m` uses RANSAC to identify wall-like structures from LiDAR points.

The configuration includes:

```text
Distance threshold   = 0.05 m
Maximum iterations   = 200
Minimum inliers      = 8
Minimum segment      = 0.5 m
Maximum segments     = 15
Scan window          = 10 scans
```

RANSAC attempts to find line structures supported by enough LiDAR points.

This is useful for identifying:

- walls
- long planar structures
- environmental boundaries

---

# 20. Map Filtering

`filterMapPoints.m` applies conservative filtering to the reconstructed map.

The objective is to reduce suspicious occupied cells while preserving genuine structures.

The filtering configuration considers:

- wall proximity
- occupied-neighbor support
- observations
- behind-wall tolerance
- corner preservation

The map builder records the number of cells removed by this filtering stage.

# 28. Understanding the Localization Error

The project evaluates position error using the Euclidean distance between estimated and ground-truth position:

```text
error = sqrt(
    (x_est - x_gt)^2 +
    (y_est - y_gt)^2
)
```

The reported results are:

```text
RMSE       = 0.0982 m
Mean error = 0.0455 m
Max error  = 0.4288 m
```

Therefore, the reported average position error is approximately 4.55 cm and the RMSE is approximately 9.82 cm for this simulation run.

The maximum error is a transient peak rather than the typical error throughout the entire trajectory.

# 31. Why the SLAM Trajectory Is Close to Ground Truth

Several factors contribute to the result:

1. The simulated environment provides repeatable geometric structures.
2. The virtual LiDAR provides dense 360° range measurements.
3. The LiDAR range noise is relatively small.
4. The robot travels through areas that produce repeated observations.
5. Loop closures provide global constraints.
6. Pose-graph optimization corrects accumulated drift.
7. The SLAM pose is aligned to the world frame using the first accepted scan.

The result should nevertheless be interpreted as **simulation performance**, not as a guarantee of the same accuracy on a physical robot.

---

# 32. Important Distinction: Ground Truth vs SLAM

The simulator has access to a ground-truth map internally.

However, the SLAM map shown in the final results is reconstructed from the simulated LiDAR scans and estimated poses.

Conceptually:

```text
Ground Truth Map
       │
       ├──> Collision checking
       │
       └──> Virtual LiDAR
                │
                ▼
           LiDAR scans
                │
                ▼
             SLAM
                │
                ▼
         Estimated poses
                │
                ▼
        Reconstructed map
```

The ground-truth map is therefore used as the simulated physical world and sensor source, while SLAM still has to estimate the robot trajectory from scans.

# 33. Computational Design

The project contains several performance-oriented decisions.

### Scan gating

Reduces redundant SLAM updates.

### Occupancy-map caching

Avoids rebuilding the complete map on every simulation step.

### Direct occupancy-grid access

The LiDAR simulator obtains the occupancy grid and performs direct grid lookups rather than repeatedly calling higher-level occupancy functions for every ray sample.

### Defensive SLAM handling

Invalid scans, rejected scans and runtime exceptions are handled without unnecessarily terminating the entire simulation.

### Modular visualization

Graphics are updated through dedicated modules rather than being embedded throughout the main loop.

# 35. Limitations

This is a controlled simulation, so the results should not be presented as real-world SLAM accuracy.

Current limitations include:

- no physical LiDAR
- no wheel encoder
- no IMU
- no camera
- simplified robot dynamics
- simulated environment
- synthetic LiDAR measurements
- Gaussian range noise rather than a full sensor-error model
- tuned perception thresholds
- no real-world calibration
- no dynamic human/vehicle obstacles
- no public benchmark dataset evaluation

The project is therefore best described as a **modular MATLAB 2D SLAM simulation and algorithm-development platform**.

# 39. Reproducibility

The simulation contains random LiDAR range noise:

```text
rangeNoise = 0.01 m
```

Therefore, unless a random seed is explicitly fixed, repeated runs may not produce exactly identical numerical results.

The trajectory, scan acceptance, loop closures, and error metrics can vary slightly between runs.

For strict experiment reproduction, set a MATLAB random seed before running the simulation, for example:

```matlab
rng(0);
main
```
